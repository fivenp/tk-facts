## 1. WHAT IT IS
--------------------------------------------------------------------------------

Positioning line (docs.testkube.io):
  "Testkube is the open testing platform for AI-driven engineering teams. It
  provides a single platform for creating, running, and analyzing test across any
  tool, any environment, and any pipeline."

Structural definition:
  Testkube consists of a Control Plane and any number of Testkube Agents. The
  Control Plane exposes a Dashboard for centralised access. Agents are deployed in
  your infrastructure to execute tests, listen for Kubernetes events, sync
  resources, and more. The Agents are 100% open source and can run standalone
  without the Control Plane.
  Source: https://docs.testkube.io

Scope — important for setting expectations:
  "Testkube focuses entirely on the Test Execution phase of the STLC, while
  integrating with tools involved in the other phases as needed."
  Source: https://docs.testkube.io/articles/testing-pipeline

How execution works:
  Test Workflows are Kubernetes Custom Resources. When triggered, the agent spawns
  a Kubernetes Job; the scheduler creates a pod; steps run sequentially as
  containers in that pod, sharing a filesystem.
  Source: https://docs.testkube.io/articles/test-workflows

## 2. DEPLOYMENT OPTIONS
--------------------------------------------------------------------------------

  Option                 | Licensing   | Agent      | Control Plane      | Dashboard
  -----------------------|-------------|------------|--------------------|----------
  Standalone Agent       | Open source | You host   | none               | no
  Cloud Control Plane    | Commercial  | You host   | Testkube hosts     | yes
  On-Prem Control Plane  | Commercial  | You host   | You host           | yes

  Source: https://docs.testkube.io/articles/install/overview

Invariant, true in all three: agents are ALWAYS deployed by you, in your own
infrastructure.

Data residency, Cloud control plane:
  "Even when using the Testkube Cloud Control Plane, your actual tests are never
  run or stored on our servers, only test logs and artifacts will be stored."
  Source: https://docs.testkube.io/articles/install/overview

Network, Cloud: outbound only. Agent initiates all traffic to agent.testkube.io:443
over gRPC (needs HTTP/2 through proxies), plus storage.googleapis.com:443 for
artifacts and logs. No ingress rules required.

Agent capabilities — an agent can have any of four:
  Runner   — executes Test Workflows            (REQUIRES A LICENCE)
  Listener — watches Kubernetes events          (no licence)
  GitOps   — syncs Testkube CRDs to the control plane (no licence)
  Webhook  — emits webhooks, CDEvents, K8s events     (no licence)
  Source: https://docs.testkube.io/articles/agents-overview

## 3. THE THREE FREE WAYS TO START
--------------------------------------------------------------------------------

A. CLOUD TRIAL — self-serve, nothing to install
   Sign up at https://app.testkube.io
   30 days, full Pro access, no credit card required.
   Comes with an automatically provisioned cloud-hosted runner, so workflows run
   immediately with no agent to install. Demo data is pre-seeded so the dashboard,
   execution history and insights are populated on first login.
   Source: https://testkube.io/pricing , https://docs.testkube.io/articles/trial-limits

B. LOCAL CONTROL PLANE — testkube init demo
   Installs the on-prem demo control plane in the current Kubernetes context in
   3-5 minutes. Requires a local Kubernetes runtime (Minikube, kind, k3s, or
   Docker Desktop's Kubernetes) and a trial licence key, passed via -l/--license.
   Preconfigured admin: admin@example.com / password
   Then run testkube dashboard for localhost access.
   This installs the CONTROL PLANE ONLY — run testkube install runner separately
   to execute workflows.
   Single/local user only. Does not create an Ingress configuration.
   Source: https://docs.testkube.io/articles/tutorial/quickstart/individual-evaluation

C. OPEN SOURCE AGENT — free forever, no account, no licence
   testkube init
   or: helm repo add kubeshop https://kubeshop.github.io/helm-charts
       helm upgrade --install testkube kubeshop/testkube \
         --create-namespace --namespace testkube --set installCRDs=true
   Dual-licensed MIT + Testkube Community License (TCL).
   Source: https://docs.testkube.io/articles/install/standalone-agent

## 5. LICENSING MECHANICS
--------------------------------------------------------------------------------

Two dimensions.
  Source: https://docs.testkube.io/articles/licensing

USERS
  Full users have write access to at least one resource, resource group or
  environment. Read-only users have write access to none.
  If a read-only user is granted write access, they count against the full user
  quota. With no seat available, the permission change is prevented.

RUNNER AGENTS
  Fixed:    licence assigned to one specific runner agent. That agent runs
            workflows whenever it is online.
  Floating: licence shared across multiple runner agents, capping how many can
            execute CONCURRENTLY. Two floating licences across ten agents means
            two run at a time; further executions queue.
  Enforced at the ORGANIZATION level, across all environments.
  Listener, webhook and GitOps agents need no licence — deploy as many as you want.

LICENCE KEYS (self-hosted control plane)
  Online format:  XXXXXX-XXXXXX-XXXXXX-XXXXXX-XXXXXX-V3
                  set via global.enterpriseLicenseKey, or a secret referenced by
                  global.enterpriseLicenseSecretRef
                  Requires outbound HTTPS to license.testkube.io:443
  Offline format: a long string prefixed with key/ plus a licence file starting
                  -----BEGIN LICENSE FILE-----
                  set global.enterpriseOfflineAccess: true
                  For air-gapped installs. Contact support to obtain one.
  Troubleshooting: testkube diag license
  Source: https://docs.testkube.io/articles/install/install-with-helm

HOW TO GET ONE
  Trial and evaluation licences are issued by the Solutions Engineering team:
  https://testkube.io/demo — the docs describe this as "not a sales call".
  There is currently no self-service licence issuance for self-hosted installs.

## 7. OPEN SOURCE vs COMMERCIAL — the capability split
--------------------------------------------------------------------------------

The split is agent-vs-control-plane, not "free tier vs paid tier". The open source
artifact is the AGENT, run in standalone mode.

NOT AVAILABLE in the open source agent standalone — workflow engine features:
  execute      complex orchestration across workflows
  parallel     parallel execution
  matrix       parameterisation, with count, shards, maxCount
  services     spawning dependencies for tests
  concurrency  concurrency policies
  Source: https://docs.testkube.io/articles/install/standalone-agent

  Consequence worth stating plainly: every distributed, sharded or parallel
  example in Testkube's own documentation requires the commercial control plane.

NOT AVAILABLE — control plane only:
  Dashboard, environment management, multi-agent environments, concurrency and
  queuing, dedicated listener/GitOps/webhook agents, control plane resource
  storage, SSO, SCIM, RBAC and user management, resource metrics, reporting and
  insights, workflow health and flakiness detection, status pages, advanced log
  and results debugging, teams, resource groups, JUnit reports, audit logs, AI
  agents, AI assistant, MCP server, test discovery.
  Source: https://docs.testkube.io/articles/install/feature-comparison

AVAILABLE in the open source agent:
  Test Workflows (with the limits above), Kubernetes event triggers, webhooks,
  the CLI, the REST API (unauthenticated), test logs and artifacts via CLI/API.

  Plus a public execution viewer: testkube view <executionId> uploads one
  execution's metadata, logs and artifacts and returns a public link on
  view.testkube.io, with no login required.
  Limits: 10 MB per execution, links expire after 4 hours, 50 active executions
  (FIFO eviction), 5 AI analyses per day.
  Privacy warning from the docs: anyone with the link can view it.
  Source: https://docs.testkube.io/articles/viewing-oss-executions

LICENSING OF THE SOURCE
  Dual-licensed: MIT for open source components, Testkube Community License (TCL)
  for specific advanced features marked "Pro" in the codebase. The TCL was
  inspired by the CockroachDB Community License. Per-feature licence is visible in
  each file's header in the repository.
  Source: https://docs.testkube.io/articles/testkube-licensing-FAQ

OFFICIAL "WHEN TO UPGRADE" TRIGGERS
  Testkube's own list, useful because it inverts into an honest "don't upgrade
  yet". Upgrade when:
    - your state of quality lives in spreadsheets, screenshots and chat threads
      instead of a dashboard
    - you run hundreds of tests a day and finding the one that failed takes longer
      than fixing it
    - multiple teams share one setup with no teams, access groups or audit trail
    - you run agents in several clusters and every new environment means another
      one-off setup
    - your suite is too large for one agent and you need parallel execution and
      sharding
    - you maintain glue scripts connecting test execution to CI/CD that break
      whenever either side changes
  Source: https://testkube.io/open-source-vs-commercial

  If none of these describe the person, the honest answer is to stay on open
  source.

--------------------------------------------------------------------------------

Testkube runs container images, so in principle anything that runs in a container
runs here. The list below is what Testkube documents with working examples — use

  E2E and browser:       Cypress (basic and sharded), Playwright (basic, sharded,
                         rerun-failed), Selenium (Chrome, Edge, Firefox),
                         Robot Framework (basic and parallelised)
  API:                   Postman, SoapUI, REST Assured, cURL
  Unit and integration:  Pytest, Maven, Gradle, NUnit, TestContainers
  Infrastructure:        Testkube Marketplace workflows, Chainsaw,
                         kubectl-based validation

DO NOT list Ginkgo, ZAP, Tracetest, Kubepug or Kubent. These existed only as
legacy executors, which were removed in v1.21.1 (December 2025), and have no

## 11. REQUIREMENTS
--------------------------------------------------------------------------------

  Kubernetes 1.21+
  Helm 3+
  Outbound internet access from the cluster

Self-hosted control plane, additionally:
  At least 3 nodes, at least 2 CPU cores and 8GB memory per node
  cert-manager 1.11+ recommended, for TLS
  Gateway API 1.7.2+ or NGINX Controller 1.8+ recommended, for service exposure
  A public or private domain, for Ingress rules
  Source: https://docs.testkube.io/articles/install/install-with-helm

Hard constraints:
  HTTP/2 must be supported end to end by your gateway or proxy. gRPC will not
  work without it. On Azure this means Application Gateway for Containers — the
  standard Azure Application Gateway does not support gRPC.
  Ingress controller: use kubernetes/ingress-nginx. Do not use nginx/nginx-inc.
  Container images must be in a registry, public or private. Local images are not
  supported — image metadata is read from the registry, not the local daemon.

## 12. KNOWN LIMITATIONS
--------------------------------------------------------------------------------

State these when relevant. They are in Testkube's own documentation.

Access control is not a hard security boundary
  "Testkube enforces resource access described in this document in the Control
  Plane, meaning that it is possible to bypass these controls by directly
  interacting with Testkube resources in your cluster(s) using kubectl or similar
  tooling. More rigorous RBAC functionality enforced across the entire Testkube
  stack is on the roadmap."
  Source: https://docs.testkube.io/articles/resource-access-management

Kubernetes is the runtime
  The agent uses Kubernetes as its runtime environment. There is one exception, a
  Docker agent via testkube docker init. The system UNDER test does not need to be
  in Kubernetes — the agent only needs network access to it.

Scope is execution, not authoring
  Testkube focuses on the test execution phase. AI-assisted test creation exists
  but is marked preview.

No native "rerun failed tests"
  "Since all testing tools have different approaches to rerunning failed tests,
  Testkube does not have a native 'Rerun failed tests' functionality."

Flakiness detection is workflow-level
  Test-level flakiness is stated as a future release, not shipped.

Trigger matching inside arrays is unsupported
  Matching on array fields such as containers[*] is not supported yet.

Granular insights metrics require PostgreSQL
  Not supported on deployments using MongoDB.

## 13. AMBIGUITIES — do not resolve these, cite both sides
--------------------------------------------------------------------------------

1. Edition naming is inconsistent across surfaces:
     testkube.io/pricing                   → "Pro" and "Enterprise"
     testkube.io/open-source-vs-commercial → "Testkube Enterprise" for all paid
     documentation                          → "On-Prem Control Plane",
                                              "Cloud Control Plane",
                                              "Standalone Agent"
     the Helm chart itself                  → testkube-enterprise
   Use Pro/Enterprise for what to buy, the docs names for how it installs.

2. Trial user count: 3 users (trial limits page) vs 3 full + 5 read-only (member
   management page). Both are cited in section 6.

3. Open source to Cloud migration: the migration guide describes execution history
   being imported; the standalone agent page says historical execution results and
   artifacts will not be copied. Workflow, trigger and webhook definitions are
   preserved in both accounts. Do not assert either version about history — tell
   the person to confirm with Testkube.
